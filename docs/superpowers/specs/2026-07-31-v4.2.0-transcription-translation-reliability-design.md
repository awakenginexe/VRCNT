# VRCNT 4.2.0 Transcription and Translation Reliability Design

Date: 2026-07-31
Status: Approved

## Context

VRCNT 4.0 can produce two related failure patterns during live speaker
transcription:

1. Whisper large-v3-turbo can emit confident-looking subtitle or channel
   boilerplate while the input contains silence or music. Those false
   transcripts currently enter the normal translation pipeline and consume
   Google or Bing requests.
2. The 4.0 translation scheduler can make a queue appear frozen and then drain
   suddenly. A job can try Google and Bing sequentially, each with a five-second
   deadline, while one translation worker owns the queue. Later jobs switch to
   the already-loaded local fallback only after the backlog grows.

VRCNT 4.1 already changes the scheduler to assign one rotating cloud provider
per message and process translation jobs independently. Version 4.2.0 will
preserve that behavior, add regression coverage, block non-speech before
translation scheduling, and close the remaining CTranslate2 readiness and
concurrency gaps.

## Goals

- Prevent silence/music hallucinations from consuming any translation request.
- Allow at most one public cloud attempt for each message.
- Alternate Google and Bing as primary providers between messages.
- Send a failed cloud message directly to CTranslate2, never to another cloud
  provider.
- Keep an opted-in CTranslate2 fallback loaded and ready while translation is
  enabled.
- Prevent one slow cloud request from blocking unrelated queued messages.
- Make parallel local translation safe when jobs use different source
  languages.
- Release the result as version 4.2.0 with automated regression coverage.

## Non-goals

- CTranslate2 will not perform speculative or shadow translations while the
  assigned cloud request is pending.
- The application will not maintain a language-specific blacklist of phrases
  such as "please subscribe" or "subtitles by volunteers." Real media can
  legitimately contain those phrases.
- Version 4.2.0 will not change the selected five-second cloud timeout.
- Version 4.2.0 will not automatically substitute Bing for Google, or Google
  for Bing, within a single message.

## Provider Routing Contract

For a selection of Google + Bing + Fallback, messages use this route:

```text
M1 -> Google -> CTranslate2 on failure, timeout, or cooldown
M2 -> Bing   -> CTranslate2 on failure, timeout, or cooldown
M3 -> Google -> CTranslate2 on failure, timeout, or cooldown
M4 -> Bing   -> CTranslate2 on failure, timeout, or cooldown
```

The following route is forbidden:

```text
M1 -> Google -> Bing -> CTranslate2
```

Provider rotation assigns exactly one cloud provider when the message is
admitted. The job may append CTranslate2 only when local fallback is enabled.
If the assigned provider is already cooling down, the job proceeds directly to
the warm local fallback without making a doomed public request.

The existing bounded 4.1 worker pool remains responsible for allowing cloud
deadlines on separate messages to elapse concurrently. Output ordering remains
the responsibility of the existing trace/output pipeline.

## CTranslate2 Readiness Contract

CTranslate2 residency is determined by translation state, primary selection,
and the fallback checkbox:

| Translation enabled | Primary engine | Fallback enabled | CTranslate2 state |
| --- | --- | --- | --- |
| No | Any | Any | Unloaded |
| Yes | CTranslate2 | Either | Loaded and ready |
| Yes | Cloud | Yes | Loaded and ready, idle until fallback |
| Yes | Cloud | No | Unloaded |

When cloud translation succeeds, the warm CTranslate2 model performs no work.
Its RAM or VRAM allocation is the explicit cost of enabling Fallback.

The controller will enforce this invariant for every state transition, not only
when the checkbox is initially selected:

- Enabling translation prepares CTranslate2 when it is primary or fallback.
- Enabling Fallback during active cloud translation prepares CTranslate2 before
  confirming the setting.
- Switching from CTranslate2 primary to a cloud primary keeps CTranslate2
  loaded when Fallback remains enabled.
- Switching tabs or engine selections re-evaluates the invariant.
- Changing the CTranslate2 weight, compute device, or compute type reloads the
  model immediately when the invariant requires it.
- Disabling Fallback unloads CTranslate2 when it is not primary.
- Disabling translation unloads CTranslate2.

Model preparation remains single-flight: one caller loads or reloads the model,
and concurrent callers observe the same readiness result. Slow model or
tokenizer cache repair occurs during activation or a settings change, never in
the hot cloud-failure path when the readiness invariant is satisfied.

If enabling Fallback cannot prepare the local model, the controller rejects the
setting and leaves cloud translation active. If enabling translation requires a
local model and preparation fails, activation fails with the existing local
translation error handling rather than advertising a fallback that is not
ready.

## Whisper Non-speech Guard

Live Whisper transcription will use acoustic voice activity detection before a
decoded result can become a transcription trace. The implementation will
upgrade `faster-whisper` from 1.1.1 to 1.2.1 and use its newer Silero VAD for
both microphone and speaker live-audio paths, with particular importance for
speaker/desktop audio containing music.

The acceptance pipeline is:

```text
audio chunk
  -> acoustic voice-activity filtering
  -> Whisper decoding
  -> existing segment confidence/no-speech checks
  -> accepted transcript
  -> translation trace and provider scheduling
```

If VAD yields no speech, or every decoded segment fails the confidence gates,
the transcriber returns no accepted transcript. Because translation traces are
created only from accepted transcripts, rejection is a hard API barrier: there
is no Google request, Bing request, CTranslate2 inference, OSC translation, or
translated UI update for that chunk.

The guard is acoustic rather than phrase-based. This avoids suppressing genuine
spoken calls to subscribe, real subtitle credits, or other valid content. VAD
parameters remain conservative to limit damage to quiet speech, and existing
confidence thresholds continue to provide a second independent signal.

The application will record privacy-safe rejection reasons and counts, without
logging transcript content, so silence/non-speech rejection can be distinguished
from low-confidence segment rejection during diagnosis.

## Parallel CTranslate2 Safety

The 4.1 scheduler may invoke CTranslate2 from multiple workers. The shared
tokenizer currently exposes mutable `src_lang` state, so one job can change that
state while another job is encoding input.

Version 4.2.0 will make tokenizer language selection and tokenization atomic.
Native CTranslate2 inference will remain outside the tokenizer critical section
so the scheduler does not reintroduce the old queue-wide serialization.
Decoding will also use the tokenizer safely. Model load/unload transitions will
continue to wait for active calls before replacing shared objects.

## Error Handling and Observability

- Each translation attempt retains a trace identifier, assigned provider,
  status, duration, and fallback transition.
- Provider logs and metrics must not include message contents.
- A cloud timeout is terminal for that cloud attempt and transitions directly
  to CTranslate2 when enabled.
- A local readiness failure is surfaced at the activation or setting change that
  caused it whenever possible.
- Queue and timing metrics will allow a regression test to distinguish parallel
  five-second cloud waits from serialized five-plus-five-second chains.

## Test Strategy

Implementation will follow test-driven development. New failing tests will be
added before each production change.

### Transcription tests

- Silence/non-speech produces no accepted transcript.
- A music-like non-speech fixture rejected by VAD creates no translation trace.
- Rejected chunks cause zero fake Google, Bing, and CTranslate2 calls.
- Valid quiet speech still reaches the accepted-transcript path under the chosen
  conservative defaults.
- Existing average-log-probability and no-speech-probability filtering remains
  effective.

### Routing and timing tests

- Messages alternate Google, Bing, Google, Bing.
- Google failure proceeds directly to CTranslate2 and never calls Bing.
- Bing failure proceeds directly to CTranslate2 and never calls Google.
- A cooling assigned provider proceeds directly to CTranslate2.
- Each message makes at most one public attempt.
- Multiple timed-out cloud messages reach local fallback independently rather
  than accumulating serial five-second waits.

### Readiness tests

- Enabling Fallback while translation is active preloads CTranslate2.
- Enabling translation with cloud + Fallback preloads CTranslate2.
- Moving from local primary to cloud + Fallback does not unload CTranslate2.
- Disabling Fallback with a cloud primary unloads CTranslate2.
- Relevant model/device/type changes refresh the warm fallback before returning.
- A preparation failure cannot leave the UI reporting an enabled but unavailable
  fallback.

### Concurrency and release tests

- Concurrent mixed-source-language jobs cannot overwrite tokenizer language
  selection.
- Load/unload waits for active local calls without deadlock.
- Existing transcription, scheduler, activation, and translation-attempt suites
  remain green.
- Python, frontend, Tauri, Cargo, and package metadata all report 4.2.0.

## Release Metadata

The release will update all existing version declarations from 4.1.0 to 4.2.0
and add release notes for:

- Whisper silence/music hallucination suppression.
- Translation API-call protection.
- One-cloud-attempt round-robin routing guarantees.
- Reliable warm CTranslate2 fallback readiness.
- Parallel local translation safety.
- Elimination of the old serialized timeout/backlog behavior.

## Risks and Tradeoffs

- A warm local fallback consumes RAM or VRAM even when cloud translation is
  healthy. This is intentional and opt-in through the Fallback checkbox.
- VAD can reject unusually quiet or atypical speech. Conservative defaults and
  valid-quiet-speech regression coverage reduce this risk.
- Dependency upgrades can alter transcription segmentation. Focused pipeline
  tests and a full relevant-suite run are required before release.
- More independent translation workers can increase burst traffic. The
  non-speech barrier, one-public-attempt rule, provider pacing, and bounded queue
  limit that exposure.

## Acceptance Criteria

The 4.2.0 work is complete when:

1. Silence/music hallucination fixtures create no translation provider calls.
2. Google and Bing alternate per message, and neither is a fallback for the
   other.
3. A failed or timed-out cloud message reaches an already-loaded CTranslate2
   fallback without model-load latency.
4. Separate messages do not accumulate serialized cloud timeout chains.
5. Mixed-language local jobs are concurrency-safe.
6. Relevant automated suites pass and every release version reports 4.2.0.
