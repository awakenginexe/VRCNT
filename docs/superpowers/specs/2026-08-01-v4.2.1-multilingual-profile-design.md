# VRCNT 4.2.1 Multilingual Conversation Profile Design

Date: 2026-08-01
Status: Approved for implementation
Base: VRCNT 4.2.0 (`codex/v4.2.0-reliability`)

## Context

VRCNT already stores three fixed language slots for the user's languages and target languages, and the translation pipeline can produce multiple target-slot results. However, the current interface hides slots two and three behind small add/remove controls, engine changes can disable saved language choices, and transcription engines do not share a clear capability policy.

Version 4.2.1 will turn these partially exposed structures into an explicit multilingual conversation profile. A user can configure up to three languages they speak, one language they understand best, and up to three target languages. The design retains the existing fixed-slot storage and progressive translation pipeline to avoid a broad migration.

## Goals

- Let users select one to three languages they speak.
- Keep exactly one preferred language for received-speech translation.
- Let users select one to three target languages.
- Translate microphone speech into every enabled target language and send every successful result to VRChat in stable target order.
- Recognize received speaker audio from the enabled target-language set and translate it into the one preferred language.
- Make multi-language behavior explicit, accessible, and understandable in the UI.
- Preserve language selections when switching between transcription engines with different capabilities.
- Keep Google multi-language transcription low-latency by running bounded language candidates concurrently.
- Preserve the 4.2.0 Whisper no-speech safeguards and cloud-to-CTranslate2 translation fallback behavior.

## Non-goals

- Supporting more than three languages in any multi-language group.
- Performing word-by-word language identification within a mixed sentence.
- Replacing the fixed slot dictionaries with dynamic arrays.
- Adding a new cloud transcription provider or migrating to the paid Google Cloud Speech API.
- Changing translation-provider round-robin or fallback routing.
- Changing VRChat message formatting, separators, or length behavior.
- Building CUDA, PyInstaller, Vite production, or Tauri artifacts during implementation of this version unless separately requested.

## Terminology and profile model

Each preset owns three ordered language groups:

1. **Languages I speak**: one to three unique language/country pairs. These guide microphone transcription. Slot `"1"` is the primary language and deterministic tiebreaker.
2. **Translate received speech to**: exactly one enabled language/country pair. This is the language the user understands best.
3. **Target languages**: one to three unique language/country pairs. These are both the languages used for outgoing translations and the expected source-language set for received speaker audio.

The maximum of three is a product limit, not an engine limit. It bounds UI complexity, recognition work, cloud request bursts, and translation fan-out.

## Configuration and migration

The existing per-preset fixed-slot structures remain authoritative:

- `SELECTED_YOUR_LANGUAGES[preset]["1".."3"]`
- `SELECTED_YOUR_TRANSLATION_LANGUAGES[preset]["1"]`
- `SELECTED_TARGET_LANGUAGES[preset]["1".."3"]`

Each slot retains `language`, `country`, and `enable`. Validation and normalization will ensure:

- enabled speaking and target entries contain one to three unique language/country pairs;
- slot `"1"` is always enabled for speaking and target groups;
- the preferred translation group has exactly one enabled entry;
- malformed or missing legacy slots are repaired from defaults without discarding valid saved entries;
- removing a language disables its slot while retaining its last value for later reuse;
- engine changes derive runtime activation without mutating or deleting saved selections.

No saved-config format migration is required. Existing one-language configurations continue to behave as before.

## Engine capability policy

A single backend capability policy will define recognition behavior and expose read-only capability information to the UI. This prevents the frontend and backend from disagreeing about active or paused slots.

### Whisper

- Supports one to three active speaking languages and one to three active received-audio languages.
- For each phrase, obtain language probabilities, filter them to the enabled language codes, and select the strongest permitted language. Slot order breaks an exact tie.
- Decode the phrase once with the selected primary language.
- Allow Whisper to preserve embedded foreign words naturally. A Chinese sentence containing an English word remains a Chinese-primary phrase; VRCNT does not split the phrase into per-word languages.
- Keep VAD, no-speech, log-probability, and generation-staleness gates from 4.2.0.

### Google web transcription

- Supports one to three active languages through independent language-hinted requests.
- Submit at most three recognition requests concurrently for the same captured audio.
- Reuse the existing per-request timeout and impose one bounded phrase-level wait rather than sequential timeout accumulation.
- Select the highest-confidence non-empty successful result. Slot order breaks equal confidence.
- Isolate candidate failures: a failed or timed-out candidate does not suppress another successful candidate.
- Do not retry candidates inside the same phrase. If every candidate fails, report one aggregate transcription failure and produce no translation work.
- The UI displays a quiet informational note when multiple languages are enabled, for example: `Google checks 3 languages in parallel`.

This behavior intentionally permits up to three Google recognition requests per spoken phrase. The user approved that bounded request trade-off in favor of lower latency.

### SenseVoice

- Supports up to three active languages from the subset supported by the selected SenseVoice model.
- Use the engine's multilingual detection and accept output only when the detected language maps to an enabled entry.
- Unsupported choices are rejected by language selection rather than silently activated.

### Vosk and Parakeet

- Their loaded recognition model uses slot `"1"` only.
- Speaking slots `"2"` and `"3"` remain saved and appear paused while either engine is active.
- For received-audio recognition, Target slot `"1"` is the only recognition hint.
- Target slots `"2"` and `"3"` remain active as outgoing translation destinations even though they cannot guide received-audio recognition with these engines.
- Switching back to Whisper, SenseVoice, or Google restores saved multi-language recognition immediately.

## Microphone data flow

1. Snapshot the current preset and active speaking-language set with the audio phrase.
2. The selected transcription engine resolves one source language according to its capability policy.
3. Apply the existing no-speech and confidence gates. Rejected audio creates no translation-provider calls.
4. Create one transcription trace carrying the detected source language and one translation target per enabled Target slot.
5. Submit target jobs through the existing progressive scheduler.
6. Preserve existing provider routing: the cloud provider assigned to the trace remains the primary, and an enabled CTranslate2 model is the only fallback after that assigned cloud provider fails.
7. Publish each target's progress independently.
8. Finalize in target-slot order. Partial success keeps successful translations and does not invent text for failed slots.
9. Send all successful translations to VRChat using the existing message-format settings and separators.

## Received-speaker data flow

1. Snapshot enabled Target languages as the expected received-audio language set.
2. Resolve one source language according to the selected transcription engine's capability policy.
3. Apply existing no-speech and confidence gates.
4. Create one translation target using the single `Translate received speech to` language.
5. Run the existing translation scheduler and fallback policy once for that target.
6. Display and optionally send the translated result according to the existing receive settings.

## UI design

The approved direction is **Layout A: Clear role cards**. The language settings area contains three explicit groups rather than hidden numbered rows:

### Languages I speak

- Render enabled selections as removable chips with flag, language, and locale.
- Show a visible count from `1 / 3` through `3 / 3`.
- Show a labeled `Add language` control until the maximum is reached.
- Prevent selection of a duplicate language/country pair.
- Display an engine-specific helper line beneath the chips.
- Render engine-paused selections distinctly with an accessible explanation; do not remove them.

### Translate received speech to

- Render one language selector with flag, language, and locale.
- Describe it as the user's preferred reading/understanding language.
- Do not display add/remove controls.

### Target languages

- Use the same chip, count, duplicate prevention, and `Add language` treatment as the speaking group.
- Explain that every enabled target receives an outgoing translation and successful translations are sent together to VRChat.
- When Vosk or Parakeet is selected, explain that only Target slot `"1"` guides received-audio recognition while all enabled targets still receive outgoing translations.

All controls use buttons, keyboard focus, accessible names, and existing localization infrastructure. The compact sidebar remains responsive without hiding selected languages.

## Swap behavior

The language swap action exchanges the complete ordered `Languages I speak` and `Target languages` sets for the current preset. `Translate received speech to` remains unchanged. The operation uses independent copies, revalidates both groups, and restarts active transcription through the existing coordinated restart path.

Because runtime engine capability is derived rather than written into the saved profile, a swap does not destroy entries that the current engine cannot actively recognize.

## Failure and concurrency behavior

- Candidate recognition work is bounded to three operations per phrase.
- Google candidate completion is generation-aware. Stopping or restarting transcription makes late results ineligible for publication.
- Aggregate one phrase-level terminal metric instead of emitting a public error for every failed Google candidate.
- Never include transcript text in telemetry.
- Whisper language selection and decoding remain protected by the shared Whisper runtime lease so unload or restart cannot invalidate in-flight inference.
- Translation targets remain independent. A target timeout or provider error never suppresses another target's success.
- Empty, silence, low-confidence, or out-of-profile recognition results terminate before translation trace creation.

## Testing strategy

All implementation tests use mocks and fixtures; they do not call real cloud APIs, load production GPU models, or build application artifacts.

### Backend tests

- Preserve and normalize legacy one-language profiles.
- Enforce one-to-three unique enabled speaking and Target entries.
- Preserve disabled slot values and all saved entries across engine changes.
- Swap complete speaking and Target sets while leaving the preferred translation language unchanged.
- Whisper selects the highest-probability enabled language and forces one decode.
- Whisper preserves a mixed-language transcript such as a Chinese-primary sentence containing an English word.
- Whisper rejects silence and low-confidence output before trace creation.
- Google launches two or three candidates concurrently rather than sequentially.
- Google selects the highest-confidence success with stable slot-order ties.
- Google accepts partial candidate success and emits one aggregate failure when all candidates fail.
- Stale Google candidates cannot publish after stop or restart.
- SenseVoice accepts only enabled supported languages.
- Vosk and Parakeet use slot `"1"` without mutating saved extra slots.
- Three microphone targets create three stable progressive result slots.
- A failed target preserves the other successful targets and VRChat output order.
- Received audio from any enabled Target language creates exactly one translation into the preferred language.
- Existing Google/Bing round-robin and CTranslate2-only fallback tests remain green.

### UI tests

- Render one-to-three speaking and Target chips with accurate counts.
- Add and remove controls enforce minimum and maximum limits.
- Duplicate choices are unavailable and explained.
- Engine helper copy and paused states match backend capability data.
- Google multi-language copy reports the active candidate count.
- Vosk/Parakeet explain the difference between incoming recognition and outgoing Target translations.
- Engine switching preserves chips and restores active state.
- Complete-set swap updates both groups but not the preferred translation language.
- Chip removal, addition, paused state, and language dialogs are keyboard and screen-reader accessible.
- All new copy exists with schema parity in every supported locale.

## Acceptance criteria

- A Whisper user can configure English (Singapore), Thai, and Chinese (Taiwan), speak a phrase primarily in any one of them, and receive one correctly labeled transcript without three full decode passes.
- A Chinese-primary phrase may retain an English word without being rejected as the wrong language.
- A Google user can enable three speaking languages and receives one result after a parallel, bounded candidate race/aggregation rather than three sequential waits.
- A user whose preferred translation language is Thai receives one Thai translation from any successfully recognized enabled Target language.
- A microphone phrase creates up to three ordered translations and sends every successful translation to VRChat.
- Switching to a single-language engine never deletes the multilingual profile.
- Existing 4.2.0 no-speech filtering, progressive translation, cloud routing, and CTranslate2 preload/fallback behavior remain intact.
- Source and UI test suites pass without running a CUDA or Tauri production build.
